# File Metadata Schema and Reverse-Engineering Method

## Purpose

The fork contains thousands of tracked files. Reading every file line-by-line in one session is not a reliable engineering method, so the repository uses a reproducible catalog plus targeted source/document review.

The catalog is generated by `engineering/scripts/build_code_catalog.py` and written to:

- `engineering/catalog/FILE_CATALOG.json` — machine-readable metadata for every tracked file.
- `engineering/catalog/README.md` — counts and regeneration instructions.
- `engineering/catalog/FUNCTION_INDEX.md` — extracted source symbols with file and line locations.

## Per-file fields

- `path` — repository-relative tracked path.
- `layer` — architectural placement inferred from path (`server`, `ui`, `database`, `adapters`, and so on).
- `role` — structural role such as source code, documentation, test fixture, migration, configuration, or deployment script.
- `domain` — keyword/path-derived domains such as auth, heartbeat-execution, runner, connectors, recovery, or Hermes integration.
- `extension` — file extension.
- `bytes`, `lines` — physical size metrics.
- `binary` — whether the file is treated as binary.
- `symbol_count` — number of extracted source symbols; full records are in `FUNCTION_INDEX.md` and the catalog's top-level `symbols` list.
- `headings` — Markdown headings where applicable.
- `imports` — JavaScript/TypeScript import specifiers.
- `environment_variables` — recognized operator/provider variable names found in text.
- `confidence` — currently `automated-structural`.

## Confidence model

- `automated-structural`: generated from path, extension, headings, regex symbols, imports, and text signals.
- `repository-derived`: manually confirmed against source/docs and suitable for architecture notes.
- `runtime-verified`: confirmed by an executed build, test, health check, or live trace.

The generated catalog only claims the first level. Human-maintained engineering files may summarize repository-derived facts. `TEST_STATUS.md` records runtime verification separately.

## Reverse-engineering workflow

1. Start with the catalog layer/domain view.
2. Read package manifests and contributor rules for the selected area.
3. Follow imports, route/service names, schema definitions, adapters, and tests.
4. Record the data/control flow in `engineering/ARCHITECTURE.md` or a dated decision.
5. Run the narrowest meaningful test or health check.
6. Upgrade a claim from structural to repository-derived or runtime-verified only when evidence supports it.
7. Regenerate the catalog after tracked-file changes.

## Limits

This catalog is not a semantic call graph, dependency vulnerability report, execution trace, or guarantee that every symbol is reachable. Regex extraction can miss dynamic code and can include declarations that are test-only, generated, or dead. Runtime behavior remains proven only by tests, logs, traces, or health checks.
